1. Introduction

1.1 Purpose

This document specifies the software requirements for the Crisis Containment Service (CoA). CoA is a web-based disaster management platform designed to aggregate, process, and disseminate critical information regarding natural hazards such as earthquakes, floods, and wildfires. This SRS covers the entire system, including data ingestion services, the administrative command-and-control dashboard, and the public-facing alert system.

1.2 Document Conventions

This document follows the standard formatting for technical specifications. Bold text is used for emphasis or key terms. Monospace font is used for file names, paths, and code snippets. Requirements priorities are explicitly stated for each system feature and are not inherited. High Priority Features are marked in red and medium priority are marked with orange.

1.4 Product Scope

CoA aims to minimize the impact of natural disasters by providing real-time data to both authorities and the public. Its primary goals are:

  • Centralizing disaster data from international sources (GDACS, SeismicPortal).
  • Providing a real-time proximity alert system with integrated escape routes to safety shelters for citizens.
  • Enabling authorities to manage emergency shelters and safe zones.
  • Disseminating alerts through standardized protocols (CAP 1.2).

Benefits include faster response times for emergency services and increased safety for individuals in affected areas.

2. Overall Description

2.1 Product Perspective

CoA is a self-contained web application designed for unified disaster monitoring. It acts as a middleware that bridges raw data from geological and meteorological centers with end-users and emergency responders. The system architecture follows the Model-View-Controller (MVC) pattern and interacts with external REST APIs and RSS feeds.

2.2 Product Functions

  • Data Synchronization: Automated fetching of earthquake, flood, and fire data.
  • Interactive Mapping: Visualization of disasters and shelters using Leaflet.js.
  • Authentication: Secure login/registration for users and specialized access for admins.
  • Proximity Detection: Automatic calculation of user danger based on geolocation.
  • Shelter Routing: Identification of the nearest safe zones during an alert.
  • Standardized Reporting: Generation of CAP-compliant XML feeds.
  • Administrative Controls: Interfaces for managing shelters and simulating disaster alerts.

2.3 User Classes and Characteristics

  • Public Users (Citizens):
    • Frequency of use: Occasional (during emergencies or for documentation).
    • Technical expertise: Low to Moderate.
    • Privileges: View disasters, check proximity, find shelters.
  • Administrators (Authorities):
    • Frequency of use: Regular (monitoring and maintenance).
    • Technical expertise: Moderate.
    • Privileges: all user privileges + manage shelters, inject test alerts

2.4 Operating Environment

  • Server-side: PHP 8.2, PostgreSQL 15, Docker-compatible environment.
  • Client-side: Modern web browsers (Chrome, Firefox, Safari) with Geolocation API and JavaScript enabled.
  • Hosting: Capable of running Docker containers for isolation and scalability.

2.5 Design and Implementation Constraints

  • No External Frameworks: The core logic is implemented in vanilla PHP to ensure transparency and performance.
  • Database: PostgreSQL.
  • Protocols: Adherence to CAP 1.2 for alert dissemination is mandatory.
  • Security: All passwords must be hashed using Bcrypt; SQL injection must be prevented via PDO prepared statements. To avoid XSS attacks, all user inputs must be sanitized and validated. Output escaping and safe DOM manipulation are a must as well.

2.7 Assumptions and Dependencies

  • External Service Stability: Assumes that GDACS and SeismicPortal APIs remain available and consistent in their data formats.
  • Geolocation Accuracy: Accuracy of proximity alerts depends on the precision of the client's device geolocation.
  • Internet Connectivity: Continuous access is required for real-time data updates.
  • Human Error: Admins must be trained to use the shelter management interface correctly to avoid misconfiguration.

3. External Interface Requirements

3.1 User Interfaces

The UI consists of a mobile-responsive dashboard featuring:

  • Map View: An interactive Leaflet.js map showing clusters of disaster events.
  • Data Tables: Filterable lists of recent floods, fires, and earthquakes with the possibility of exporting to CSV.
  • Alert Overlays: Modal dialogs that trigger when a user is within 100km of a recent disaster.
  • Admin Panel: Specialized forms for managing shelter coordinates and triggering data syncs.

3.2 Hardware Interfaces

The software interacts with:

  • GPS/Geolocation Hardware: Via the browser's Geolocation API to determine user position for proximity checks.
  • Network Interfaces: Standard Ethernet/Wi-Fi/Cellular for HTTP communication.

3.3 Software Interfaces

  • Database: PostgreSQL (relational storage).
  • Operating System: OS-agnostic
  • External APIs: GDACS RSS (XML), SeismicPortal (GeoJSON), Leaflet.js.

3.4 Communications Interfaces

  • HTTP/HTTPS: Primary protocol for web access and API communication.
  • RSS 2.0 / CAP 1.2: For standardized alert dissemination via /api/cap.
  • JSON: For internal communication between the frontend and the PHP controllers.

4. System Features

4.1 Disaster Data Synchronization

4.1.1 Description and Priority

Automatically fetches and parses data from GDACS and SeismicPortal once every 5 minutes. Priority: High

4.1.2 Stimulus/Response Sequences

  • Stimulus: The request of generating a CAP feed
  • Response: System connects to external APIs, parses XML/JSON, and inserts new records into floods, fires, and earthquakes tables.

4.1.3 Functional Requirements

  1. REQ-SYNC-1: The system shall parse GDACS RSS items for coordinates, event type, and timestamp.
  2. REQ-SYNC-2: The system shall parse SeismicPortal GeoJSON for magnitude, depth, and region.
  3. REQ-SYNC-3: The system shall prevent duplicate entries using external_id constraints.

4.2 Real-time Proximity Alerting

4.2.1 Description and Priority

Calculates the distance between the user and recent disasters. Priority: High

4.2.2 Stimulus/Response Sequences

  • Stimulus: User loads the dashboard and grants location permissions.
  • Response: System executes the Haversine algorithm; if a disaster is <100km and <60 min old, a warning pop up is displayed.

4.1.3 Functional Requirements

  1. REQ-PROX-1: The system shall use the Haversine formula for distance calculation.
  2. REQ-PROX-2: The system shall identify the nearest shelter if a danger state is detected.

4.3 Shelter Management (Admin)

4.1.1 Description and Priority

Allows authorities to define safe zones. Priority: Medium

4.1.2 Stimulus/Response Sequences

  • Stimulus: Admin clicks on the map to set a shelter location and fills the capacity form.
  • Response: System stores the coordinates and metadata in the shelters db table.

4.1.3 Functional Requirements

  1. REQ-ADMIN-1: Only users with the admin role shall access the shelter management and manual alert injection interfaces.
  2. REQ-SHELTER-2: Shelters shall be displayed on the public map as distinct markers.

5. Other Nonfunctional Requirements

5.1 Performance Requirements

  • Latency: API responses for disaster listings AND emergency alerts should be under 500ms.

5.2 Safety Requirements

  • Data Integrity: Ensure that disaster coordinates are never corrupted, as this could lead to incorrect safety routing.
  • Emergency Availability: The system should prioritize minimal asset loading to remain functional under low-bandwidth emergency conditions.

5.3 Security Requirements

  • Authentication: Passwords must be hashed using PASSWORD_BCRYPT.
  • Authorization: Strict session-based role checks (Admin vs User).
  • Input Validation: All inputs must be sanitized using filter_input.
  • SQL Injection Prevention: Use PDO prepared statements for all database interactions.

5.4 Software Quality Attributes

  • Maintainability: Clean MVC separation allows for easy addition of new disaster sources.
  • Usability: Minimalist interface designed for high-stress situations. It should not be bloated.
  • Portability: Dockerization ensures consistent behavior across developer and production environments.

5.5 Business Rules

  • Admin Enrollment: Admins cannot sign up via the public form; they must be manually inserted into the database by a system owner.
  • Alert Threshold: Proximity alerts are strictly limited to events within the last 60 minutes to prevent alarm fatigue.
