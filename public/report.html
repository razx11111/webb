Team: Gheoca Razvan & Stupu Eduard

Abstract

This document provides a comprehensive System Requirements Specification (SRS) for the Crisis Containment Service (CoA), following the IEEE 830-1998 standard. CoA is a disaster management platform designed to aggregate, process, and disseminate critical information regarding natural hazards such as floods, wildfires, and earthquakes.

1. Introduction

1.1 Purpose

The purpose of this document is to define the technical requirements and architectural design for the CoA platform. It serves as a blueprint for developers and a reference for stakeholders to understand the system's capabilities in disaster mitigation.

1.2 Scope

The CoA system centralizes data from international sources (GDACS, SeismicPortal) and provides a command-and-control center for authorities. It includes proximity alerts, shelter routing, and standardized data feeds using the Common Alerting Protocol (CAP 1.2).

1.3 Definitions and Acronyms

  • CAP: Common Alerting Protocol (v1.2).
  • GDACS: Global Disaster Alert and Coordination System.
  • EMSC: European-Mediterranean Seismological Centre.
  • SOA: Service-Oriented Architecture.
  • MVC: Model-View-Controller.

1.4 References

  • IEEE Std 830-1998: Recommended Practice for Software Requirements Specifications.
  • OASIS Standard: Common Alerting Protocol v1.2.

2. Overall Description

2.1 Product Perspective

CoA is a standalone disaster management system that interacts with external sensors and data providers via REST APIs and RSS feeds. It is designed to be highly available and resilient, using Docker for infrastructure consistency.

2.2 Product Functions

  • Automated data ingestion and normalization from heterogeneous sources.
  • Real-time geolocation-based proximity hazard detection.
  • Dynamic shelter identification and path routing.
  • Standardized XML/RSS alert dissemination for third-party consumers.

2.3 User Characteristics

  • Public Users: Citizens seeking immediate hazard information and safe routes.
  • Authorities/Admins: Specialized personnel who manage safe zones and verify alert data.

2.4 Constraints

The system must operate without external PHP frameworks to ensure minimal overhead and maximum control over security and performance. It requires a modern browser with Geolocation API support.

2.5 Assumptions and Dependencies

  • External API Availability: It is assumed that GDACS and EMSC services remain operational and their XML/JSON schemas remain stable.
  • Network Connectivity: The system depends on persistent internet access to fetch real-time disaster data and serve mapping tiles.
  • Client Geolocation: Proximity alerts assume that users grant permission for location access in their browsers.

3. Specific Requirements

3.1 System Architecture

The system follows a strict MVC pattern coupled with an SOA philosophy.

  • Core Layer: Custom Router (regex-based) and Singleton Database handler.
  • Service Layer: DataSync for async fetching and CAPService for XML orchestration.

3.2 Functional Requirements

3.2.1 Proximity Detection (Haversine Algorithm)

The system calculates great-circle distances using: d = 2R * arcsin(sqrt(sin²(Δφ/2) + cos φ1 * cos φ2 * sin²(Δλ/2))). Threshold: 100km radius for events within the last 60 minutes.

3.2.2 API Specifications

  • GET /api/disasters: Consolidated JSON output.
  • GET /api/cap: RSS 2.0 with embedded CAP 1.2 XML.
  • GET /api/proximity-check: Server-side distance validation.

3.3 External Interface Requirements

  • User Interface: Responsive HTML5/CSS3 dashboard with Leaflet.js map visualization.
  • Software Interfaces: PostgreSQL 15, GDACS RSS Feed, SeismicPortal GeoJSON API.

3.4 Non-Functional Requirements

  • Security: Bcrypt hashing for credentials and PDO prepared statements for SQLi prevention.
  • Performance: Asynchronous data syncing and lightweight vanilla PHP execution.
  • Usability: Mobile-first responsive design for high-stress emergency environments.

4. Database Design

Relational schema optimized for geospatial storage:

  • Normalization of coordinates using DECIMAL(9,6).
  • Distinct tables for earthquakes, floods, and fires to support type-specific attributes.
